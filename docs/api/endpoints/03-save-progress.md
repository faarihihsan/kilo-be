# 3. save-progress

`PUT /v1/progress/{id}` — auth: bearer, role `user` only (admin gets 403)

Save one **completed** workout session log (exercises, sets, time consumed, notes). Serves as both create and update: **idempotent upsert** keyed by client-generated `id`, so the mobile app can retry safely and re-send after reconnect.

Decisions (agreed):
- Server stores **completed sessions only**. An in-progress workout lives only on the phone until the user finishes it, then the app calls this endpoint. There is no `status` field.
- Sessions can be edited later (same `PUT`) and deleted ([16-delete-progress](16-delete-progress.md)).
- Relational tables, not `jsonb`.
- No exercise name stored or returned in the log; the app resolves names from the exercise master list (endpoint 8).

## Request

Path: `id` — UUID generated by the client.

```json
{
  "workout_plan_id": "0195f3a2-aaaa-7000-8000-000000000001",
  "name": "Push Day A",
  "notes": "Felt strong",
  "started_at": "2026-09-19T08:00:00Z",
  "ended_at": "2026-09-19T08:55:00Z",
  "duration_seconds": 3120,
  "updated_at": "2026-09-19T08:55:02Z",
  "exercises": [
    {
      "exercise_id": "0195f3a2-bbbb-7000-8000-000000000010",
      "position": 0,
      "notes": null,
      "sets": [
        {
          "position": 0,
          "type": "warmup",
          "reps": 12,
          "weight": 40.0,
          "duration_seconds": null,
          "distance_meters": null,
          "rpe": null,
          "completed": true
        },
        {
          "position": 1,
          "type": "normal",
          "reps": 8,
          "weight": 80.0,
          "duration_seconds": null,
          "distance_meters": null,
          "rpe": 8.5,
          "completed": true
        }
      ]
    }
  ]
}
```

| Field | Type | Required | Rules |
|-------|------|----------|-------|
| workout_plan_id | uuid \| null | no | if set: must belong to the caller (a soft-deleted plan is fine, history stays valid). Null = freestyle workout |
| name | string | yes | 1–100 |
| notes | string \| null | no | max 2000 |
| started_at | timestamp | yes | |
| ended_at | timestamp | yes | ≥ started_at |
| duration_seconds | int | yes | time consumed (active workout time, may be less than ended − started when paused), 0–86400 |
| updated_at | timestamp | yes | client's last-modified time; drives the [conflict rule](#conflict-rule). Not more than 5 min in the future |
| exercises[] | array | yes | may be empty; max 50 |
| exercises[].exercise_id | uuid | yes | must exist in exercise master. **Soft-deleted exercises are accepted**, so an offline save never fails because another phone deleted the exercise |
| exercises[].position | int | yes | ≥ 0, unique within session |
| exercises[].notes | string \| null | no | max 1000 |
| exercises[].sets[] | array | yes | max 100 |
| sets[].position | int | yes | ≥ 0, unique within exercise |
| sets[].type | enum | yes | `warmup` \| `normal` \| `drop` \| `failure` |
| sets[].reps | int \| null | no | ≥ 0 |
| sets[].weight | decimal \| null | no | ≥ 0, kg, max 2 decimals |
| sets[].duration_seconds | int \| null | no | for timed exercises, ≥ 0 |
| sets[].distance_meters | decimal \| null | no | for cardio, ≥ 0 |
| sets[].rpe | decimal \| null | no | 1–10, step 0.5 |
| sets[].completed | bool | yes | |

Semantics: the request is the **full state** of the session (replace, not patch). The server replaces the exercises and sets in one transaction. No rest timer per set.

## Conflict rule

Let `stored` = the existing row's `updated_at` (client-supplied value from its last accepted save).

| Case | Result |
|------|--------|
| No row with this `id` | create → **201** |
| Row is soft-deleted | **409** `conflict`, `details: [{issue: "deleted"}]`. Deleted wins; the app should drop its local copy |
| request `updated_at` < stored | **409** `conflict`, `details: [{issue: "stale", current: {…}}]`, where `current` is the server's current copy (`error.details[0].current`). The app decides: keep server copy, or re-save with a newer `updated_at` if the user's edit should win |
| request `updated_at` == stored | **200**, no change, returns stored copy. This makes a retry after a lost response safe |
| request `updated_at` > stored | replace → **200** |

Also: `updated_at` more than 5 min in the future → 422 (protects against a phone with a wrong clock blocking later edits).

The server keeps a **separate** `server_updated_at` (set to now on every accepted write). Sync pulls (`updated_since`) use `server_updated_at`, because an offline upload carries an old client time and other phones would otherwise never see it.

## Responses

**201 Created** (new) / **200 OK** (updated or no-op) — returns the saved object, same shape as [get-progress](04-get-progress.md).

| Status | code | Case |
|--------|------|------|
| 400 | `bad_request` | malformed JSON, unknown field, bad path id |
| 401 | `unauthorized` | |
| 403 | `forbidden` | caller is admin |
| 404 | `not_found` | `id` exists but owned by another user (never reveal) |
| 409 | `conflict` | `stale` or `deleted`, see above |
| 422 | `validation_failed` | rules above; unknown `exercise_id`; unknown/other user's `workout_plan_id`; duplicate positions; `updated_at` too far in future |

## Data to persist

`progress`

| Column | Notes |
|--------|-------|
| id | UUID, client-generated, PK |
| user_id | FK users |
| workout_plan_id | nullable FK workout_plans |
| name, notes | |
| started_at, ended_at, duration_seconds | |
| client_updated_at | API field `updated_at`; conflict check |
| created_at | server, first insert |
| server_updated_at | server, every accepted write and delete; sync cursor |
| deleted_at | nullable, soft delete |

`progress_exercises`: id, progress_id (FK, cascade), exercise_id (FK exercises), position, notes. Unique `(progress_id, position)`.

`progress_sets`: id, progress_exercise_id (FK, cascade), position, type, reps, weight `numeric(7,2)`, duration_seconds, distance_meters `numeric(9,2)`, rpe `numeric(3,1)`, completed. Unique `(progress_exercise_id, position)`.

Child rows are deleted and re-inserted on every accepted save (same transaction).

Indexes: `progress(user_id, started_at DESC)`, `progress(user_id, server_updated_at, id)`, `progress_exercises(exercise_id)` (for future per-exercise history/stats).
