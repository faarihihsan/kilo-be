# 10. save-workout-plan

`PUT /v1/workout-plans/{id}` — auth: bearer, role `user` only (admin gets 403)

Create or update a workout plan of the current user. **Idempotent upsert** keyed by client-generated `id`, same pattern and conflict rule as [save-progress](03-save-progress.md).

A plan is **one flat list of exercises** (agreed), e.g. "Push", "Pull", "Legs" as three separate plans, or "Chest", "Legs", "Back". No days/sections.

## Request

Path: `id` — UUID generated by the client.

```json
{
  "name": "Push",
  "description": "Chest / shoulders / triceps",
  "updated_at": "2026-09-19T09:00:00Z",
  "exercises": [
    {
      "exercise_id": "0195f3a2-bbbb-7000-8000-000000000010",
      "position": 0,
      "target_sets": 4,
      "target_reps": 8,
      "target_reps_max": 10,
      "target_weight": 80.0,
      "target_duration_seconds": null,
      "target_distance_meters": null,
      "rest_seconds": 120,
      "notes": "Pause on chest"
    }
  ]
}
```

| Field | Type | Required | Rules |
|-------|------|----------|-------|
| name | string | yes | 1–100, free text. Duplicates allowed |
| description | string \| null | no | max 1000 |
| updated_at | timestamp | yes | client's last-modified time, drives the [conflict rule](03-save-progress.md#conflict-rule). Not more than 5 min in the future |
| exercises[] | array | yes | may be empty (draft plan); max 50 |
| exercises[].exercise_id | uuid | yes | must exist in exercise master (soft-deleted accepted, same reason as progress). Same exercise may repeat |
| exercises[].position | int | yes | ≥ 0, unique within plan |
| exercises[].target_sets | int | yes | 1–20 |
| exercises[].target_reps | int \| null | no | ≥ 1 |
| exercises[].target_reps_max | int \| null | no | needs `target_reps`, ≥ `target_reps` |
| exercises[].target_weight | decimal \| null | no | ≥ 0, kg, max 2 decimals |
| exercises[].target_duration_seconds | int \| null | no | ≥ 0 |
| exercises[].target_distance_meters | decimal \| null | no | ≥ 0 |
| exercises[].rest_seconds | int \| null | no | 0–3600 |
| exercises[].notes | string \| null | no | max 1000 |

Semantics: request is the **full state** of the plan (replace, not patch). Exercises are replaced in one transaction.

Limit: max **100 active plans** per user. Creating a new one beyond that → 422 (`issue: plan_limit`). Updates of existing plans are not affected.

## Conflict rule

Identical to [save-progress](03-save-progress.md#conflict-rule): no row → 201; soft-deleted → 409 `deleted`; older `updated_at` → 409 `stale` with the server copy; equal → 200 no-op; newer → 200 saved. `server_updated_at` is set on every accepted write (sync cursor).

## Responses

**201 Created** (new) / **200 OK** (updated or no-op) — returns the saved plan, same shape as [get-workout-plan](07-get-workout-plan.md).

| Status | code | Case |
|--------|------|------|
| 400 | `bad_request` | malformed JSON, unknown field, bad path id |
| 401 | `unauthorized` | |
| 403 | `forbidden` | caller is admin |
| 404 | `not_found` | `id` exists but owned by another user (never reveal) |
| 409 | `conflict` | `stale` or `deleted` |
| 422 | `validation_failed` | rules above; unknown `exercise_id`; duplicate `position`; `plan_limit`; `updated_at` too far in future |

## Data to persist

`workout_plans`

| Column | Notes |
|--------|-------|
| id | UUID, client-generated, PK |
| user_id | FK users |
| name, description | |
| client_updated_at | API field `updated_at`; conflict check |
| created_at | server, first insert |
| server_updated_at | server, every accepted write and delete; sync cursor |
| deleted_at | nullable, soft delete |

`workout_plan_exercises`: id, workout_plan_id (FK, cascade), exercise_id (FK exercises), position, target_sets, target_reps, target_reps_max, target_weight `numeric(7,2)`, target_duration_seconds, target_distance_meters `numeric(9,2)`, rest_seconds, notes. Unique `(workout_plan_id, position)`.

Indexes: `workout_plans(user_id, server_updated_at, id)`, `workout_plans(user_id, lower(name), id)`.

Child rows are deleted and re-inserted on every accepted save (same transaction).

## Notes

- Editing a plan does not touch existing progress logs; each log stores its own exercises, so history stays intact.
- Deleting a plan: [17-delete-workout-plan](17-delete-workout-plan.md).
